# AI 翻车案例库

> 本仓库最值钱的文档。每条 = 一个面试故事：错在哪 → 怎么发现 → 怎么防再发。
> 记录纪律：当天发生当天记；宁可记小，不可漏记；禁止事后美化。

分类参考：边界条件 / 并发 / 依赖版本 / 幻觉 API / 安全 / 性能 / 需求理解偏差

| # | 日期 | 场景 | AI 错在哪 | 怎么发现的 | 修复 | 防再发措施 |
|---|---|---|---|---|---|---|
| 1 | 2026-10-25 | LlmClient 单测（llm 模块） | 用 MockRestServiceServer.bindTo(builder) 打桩后，LlmClient 构造器里又调 builder.requestFactory(设置超时)，把 mock 工厂整体替换成了真实 HTTP 工厂——6 个测试中 3 个根本没走 mock，请求直接打到真实网络域名；超时测试还因"域名不可达"碰巧给出符合断言的异常消息，制造假象 | mvn verify 单测失败：状态码断言与实际异常消息不符，追查后定位 | 弃用请求级 mock，改用 JDK 自带 HttpServer 起本地真实端点做测试（零新依赖，且多覆盖了真实的请求序列化/响应反序列化路径） | mock 与被测对象共享同一个 builder 时，后设置的 requestFactory 会覆盖 mock 绑定的工厂；HTTP 客户端类优先用本地真实服务端打桩 |
| 2 | 2026-10-25 | LlmClient 异常处理（llm 模块，生产代码 bug） | chat() 只捕获 RestClientResponseException 与 ResourceAccessException 两类；读超时的 SocketTimeoutException 在该路径被 Spring 包成通用 RestClientException 裸逃（用户会看到 500 而非友好的 502）；且 Spring 对 IO 类失败的包装类型不统一，按异常类型分支本身不可靠 | 单测：改用静默 ServerSocket 确定性模拟超时后，断言异常消息不符，暴露分类缺口 | 删除按类型的分支，改为按根因链分类（根因含 IOException → 判定"不可达或超时"） | 外部调用边界的异常处理必须测试"非预期包装"路径；失败分类基于根因链而非框架包装类型 |
| 3 | 2026-10-25 | API 错误分支断言（api 模块） | ① MockMvc 断言只写 `$.error` 存在性，而 Spring 默认错误体恰好也有 error 字段——异常映射器（Advice）从未被真正验证过，属假绿灯 ② 冒烟时在 git-bash 用 curl 发中文 body，被按 GBK 编码送出导致 JSON 解析失败，一度误判为 Advice 失效 | 真实启动冒烟：短 JD 的 400 返回体是 Spring 默认格式而非自定义消息；查启动日志确认首发现象是编码问题，改 ASCII payload 后定位真因 | 断言强化到具体错误消息文本；冒烟改用 ASCII payload 验证 400/404/502 三条自定义消息全通过 | 存在性断言（field exists）对"字段重名"的默认错误体无鉴别力，错误分支断言必须落到具体值；MockMvc 全绿 ≠ 真实运行正确，交付前冒烟一次；Windows git-bash 的 curl 中文 body 不可靠，冒烟用 ASCII 或从文件读 body |
| 4 | 2026-10-25 | v1 用户自验首跑 502（llm/api 模块，可观测性缺陷） | 502 把根因完全吞掉：无启动配置自检、无服务端失败日志，用户撞 502 后（横幅只说"暂时离线"）无法自助排查是配置没注入、端点错、还是网络问题 | 用户自用报告 502；排查时发现服务端对失败全盲 | LlmClient 增加 @PostConstruct 启动自检（base-url/model/api-key 已配置与否，8081 实测）；ApiExceptionHandler 增加 WARN 根因日志（实测打印"根因 ConnectException: Connection refused"） | 任何面向用户的失败，服务端日志必须能定位到根因类别；配置类问题应在启动时第一时间暴露，而不是等第一发请求 |
| 5 | 2026-10-25 | 上述 502 排障过程（连环低级错误，如实记） | ① 用 PATH 上的 Java 11 跑 Java 17 的 jar——违反本机已知约束（PATH java 是 11，须用 mvn 或 JDK17 全路径），实例根本没起来（UnsupportedClassVersionError）② 未确认自己实例启动成功就发 curl，把 8080 上**别人实例**的响应当成自己实例的行为分析，排查方向被带偏（先怀疑僵尸进程）③ 历史冒烟收尾从不验证 kill/taskkill 是否生效：taskkill 带 WINDOWTITLE 过滤器实际匹配不到后台进程，`kill $!` 对 Windows 原生进程也常静默失败——smoke1 的 fork 进程至少存活到 smoke2 期间（其响应即为证据） | LinkageError 日志 + netstat 端口归属 + PowerShell 进程命令行逐一核查 | JDK17 全路径启动；请求前先确认自己实例端口与启动日志；taskkill //F //PID 精确杀 + netstat 复核端口已释放（本轮 8081 验证通过） | 冒烟三步缺一不可：启动确认（健康检查+端口归属核验）→ 请求验证 → 清理验证（netstat）；"我以为杀掉了"不算杀掉，必须验证 |
| 6 | 2026-10-25 | v1 代码审查（人类发起，AI 执行逐文件审查） | 两处并发缺陷：① `answer` 接口是"读-改-写"三步非原子——并发提交（双开标签页/双击）时后一次保存整体覆盖前一次，**丢答案**；② `evaluate` 在 LLM 调用 60~90 秒期间持有的会话快照会过期——结束时用快照 `withStatus` 整体替换，**抹掉评估期间新提交的答案**，且并发双评估可双烧 LLM 双写报告。另有 baseUrl 尾斜杠拼接 `//`、spec 与实现的配置校验口径不一致两处小问题 | 人类要求的代码审查轮（AI 逐文件审查发现；单测此前全绿——并发时序问题不在单测射程内） | store 新增 `updateSession(id, UnaryOperator)`（ConcurrentHashMap.compute 原子读改写）；answer 与 evaluate 的状态声明全部改走原子路径；补 7 个测试含"评估期间新答案不被抹掉"回归测试。尾斜杠归一化、spec 口径对齐 | "内存单用户就不管并发"是错误直觉——浏览器双开标签页就是并发；多步状态变更必须用存储层原子原语，而非调用方自行 read-modify-write；并发类缺陷单测测不出来，靠审查 |
